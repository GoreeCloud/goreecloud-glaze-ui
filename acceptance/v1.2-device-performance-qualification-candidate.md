# GLAZE UI V1.2 — Physical-Device and Production-Performance Qualification Candidate

**Lifecycle:** Candidate protocol only  
**Stable baseline:** GLAZE UI V1.1 / `1.1.0`  
**V1.2 authority:** `1.2.0-candidate`, opt-in, non-consumer-eligible  
**Promotion relationship:** Companion evidence procedure for G4 and later exact-head release review; this document does not mark any gate passed.

## Purpose

This procedure defines how real physical-device and production-performance observations are attached to one exact V1.2 source revision. It exists because browser CI and Android emulators provide useful bounded observations but cannot establish GPU/compositor, memory, power, thermal, OEM, constrained-device, or production performance acceptance.

The machine-readable authority is `contracts/v1.2/device-performance-qualification.candidate.json`. Records are validated by `scripts/validate_glaze_v1_2_device_performance_qualification.py`.

## Canonical budget boundary

`contracts/performance/glaze-v1-performance-budget.json` currently has status `revalidation-required`. No accepted numeric runtime or platform budgets are currently authoritative.

Therefore:

- measurements may be captured and retained as observations;
- this protocol must not invent FPS, frame-time, jank, latency, memory, GPU, compositor, power, or thermal thresholds;
- an evidence record cannot use decision `accepted` while the canonical budget remains `revalidation-required`;
- browser CI, Android emulators, simulators, synthetic fixtures, and protocol self-tests cannot satisfy physical-device qualification;
- one device cannot establish an entire platform or OEM matrix.

## Exact-revision requirement

Every real record must contain the exact 40-character lowercase Git revision being tested and must validate against the checked-out revision. `latest`, branch names, moving tags, abbreviated SHAs, or reused evidence from an earlier revision are prohibited.

Before capture:

1. Check out the exact target revision.
2. Confirm `VERSION`, `currentStable`, and `currentOfficial` remain `1.1.0` while V1.2 is Candidate.
3. Record the physical device manufacturer/model, OS version/build, architecture, GPU, and display refresh rate.
4. Record power source, battery percentage, initial thermal state, controlled background-load condition, appearance mode/matrix, and active accessibility modes.
5. Use a real physical device. Set `physicalDevice: true` and `emulator: false` only when that is factually true.

## Required scenario matrix

A record must cover every protocol scenario:

- `appearance-light-dark-deep-dark`
- `clarity-clear-balanced-dense`
- `living-glaze-tier-3-to-0`
- `productive-scroll-and-large-list`
- `navigation-and-interaction`
- `large-text-200-touch-assistance`
- `reduced-transparency-and-motion`
- `personalization-and-atmosphere`

Each scenario records the required metric families:

- frame timing / frame pacing;
- interaction latency;
- memory;
- compositor or GPU behavior;
- power;
- thermal behavior.

A metric may be `measured` with a finite numeric value and explicit unit, or `not-available-with-reason` for observation-only records when the platform/tooling cannot expose that metric. An eventual `accepted` record requires all required metrics to be measured under an accepted canonical budget.

## Visual, semantic, and accessibility preservation

Performance degradation is not allowed to sacrifice:

- content or task completion;
- semantic state;
- focus and keyboard/touch reachability;
- 48 px baseline targets or 56 px assisted targets;
- Reduced Transparency/Reduced Motion behavior;
- truthful loading/error/recovery state;
- readable text and hierarchy.

The Tier 3 → Tier 2 → Tier 1 → Tier 0 degradation path must reduce optional atmosphere/effects before semantics or accessibility.

## Evidence decision meanings

- `observation-only` — measurements were captured, but no production acceptance is claimed.
- `not-accepted` — the tested revision/device configuration has a blocking performance or fidelity finding.
- `accepted` — reserved for a future state where the canonical budget itself is accepted and the record satisfies all exact-revision, physical-device, scenario, metric, and review requirements. The current Candidate validator intentionally rejects this decision while the budget is `revalidation-required`.

## Validation

Validate protocol/source boundaries and synthetic negative cases:

```bash
python scripts/validate_glaze_v1_2_device_performance_qualification.py --self-test
```

Validate a real record against the currently checked-out exact revision:

```bash
python scripts/validate_glaze_v1_2_device_performance_qualification.py --record /path/to/device-performance-record.json
```

The self-test deliberately exercises valid format handling and rejection of stale revisions, emulators posing as physical devices, placeholder hardware data, missing metric families, and production acceptance without an accepted canonical budget. Self-test records are synthetic and are never evidence.

## Completion boundary

This protocol is complete when its source contract, validator, and CI self-tests are exact-head green. **Physical-device performance acceptance remains incomplete** until real records exist for the governed representative device/platform matrix and the canonical numeric/platform budgets have been separately accepted. RC, Stable, and consumer conformance remain separate governed decisions.
