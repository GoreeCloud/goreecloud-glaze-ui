# GLAZE UI V1.2 — Manual Assistive-Technology Qualification Candidate

**Lifecycle:** Candidate protocol only  
**Stable baseline:** GLAZE UI V1.1 / `1.1.0`  
**V1.2 authority:** `1.2.0-candidate`, opt-in, non-consumer-eligible  
**Promotion relationship:** Companion evidence procedure for G4 and later exact-head release review; this document does not mark accessibility acceptance complete.

## Purpose

This procedure defines how real manual assistive-technology sessions are recorded against one exact V1.2 source revision. Machine accessibility trees, DOM semantics, UIAutomator, and emulator checks remain valuable but do not prove how TalkBack, Voice Access, Switch Access, VoiceOver, Switch Control, Orca, or another claimed assistive technology behaves for a person on real hardware.

The machine-readable authority is `contracts/v1.2/assistive-technology-qualification.candidate.json`. Records are validated by `scripts/validate_glaze_v1_2_assistive_technology_qualification.py`. Start each real record from `acceptance/v1.2-assistive-technology-qualification.template.json`; the template intentionally defaults to a failed, non-manual state and is never evidence by itself.

## Exact-revision and human-operation requirements

Every real session record must:

- begin as a copy of the fail-closed qualification template rather than mutating the canonical template itself;
- identify the exact 40-character lowercase Git revision being evaluated;
- name the repository as `GoreeCloud/goreecloud-glaze-ui`;
- identify the human operator/reviewer;
- set `manualExecution: true` only after a real manual session;
- identify platform, physical device manufacturer/model, OS version/build, assistive-technology name/version, and input mode;
- use a physical device for physical qualification (`physicalDevice: true`, `emulator: false`);
- record scenario-level pass/fail/not-applicable-with-reason outcomes and concrete observations;
- identify a defect/finding for every failed scenario.

Moving aliases, abbreviated SHAs, copied findings from another revision, placeholders such as TBD/unknown, or machine-only execution represented as manual evidence are prohibited.

## Recognized assistive technologies

The protocol can record sessions for:

- TalkBack;
- Voice Access;
- Switch Access;
- VoiceOver;
- Switch Control;
- Orca;
- another explicitly named technology via `Other`.

The applicable support matrix is governed by the actual supported/claimed platforms. A session for one technology or platform does not imply acceptance for another.

## Required scenario matrix

Every session record covers:

- `launch-and-orient`
- `navigate-primary-destinations`
- `activate-primary-actions`
- `focus-order-and-reachability`
- `names-roles-states-and-values`
- `error-status-and-recovery-announcement`
- `large-text-200-percent`
- `reduced-transparency`
- `clarity-and-personalization-controls`

Reviewers should record what was actually spoken, exposed, focused, activated, announced, or blocked—not merely what the source code intends.

## Required observation dimensions

Manual review should explicitly cover:

- spoken/presented name;
- role and state/value;
- focus order;
- action reachability;
- dynamic-state announcements;
- error and recovery feedback;
- 200% large-text reflow and reachability;
- accessibility-preference precedence over decorative Glaze behavior.

Where a technology uses voice commands or switches rather than touch exploration, record the concrete input method and command/switch path used.

## Session decision meanings

- `session-pass` — the required scenarios in this one session contain no failed scenario. This is **not** full product or support-matrix accessibility acceptance.
- `session-fail` — one or more required scenarios have a blocking/manual finding.

A single passing TalkBack, VoiceOver, Voice Access, switch-control, or Orca session cannot by itself establish complete native-platform accessibility parity, physical-device accessibility acceptance, RC, Stable, or consumer conformance.

## Validation

Validate the protocol and synthetic negative cases:

```bash
python scripts/validate_glaze_v1_2_assistive_technology_qualification.py --self-test
```

Validate a real manual session against the currently checked-out exact revision:

```bash
python scripts/validate_glaze_v1_2_assistive_technology_qualification.py --record /path/to/assistive-technology-record.json
```

The self-test verifies format handling and rejects stale revisions, machine-only sessions, emulators represented as physical evidence, placeholder technology versions, and a `session-pass` containing a failed scenario. Self-test records are synthetic and are never manual or physical-device evidence.

## Completion boundary

This protocol is complete when its source contract, fail-closed template, validator, procedure, and CI self-tests are exact-head green. **Manual assistive-technology acceptance remains incomplete** until the applicable real supported-platform/device/technology matrix has been executed by people and its exact-revision evidence reviewed. Human optical acceptance, production performance, RC, Stable, and consumer conformance remain independent gates.
